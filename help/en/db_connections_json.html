Database connections — files, SQL templates and dialects (WysiQ)

This note explains how the fields you see in Data Sources map to files on disk,
how connectors are resolved to a database engine, where SQL templates live, and
how identifier quoting is handled per dialect.
See also: help/en/datasource.txt (the Data Sources window)
          help/en/params_db_connection.txt (profile JSON files)
          help/en/save_dialog_create.txt (local CREATE and exports)
1) The four levels
WysiQ separates four things. Keeping them apart is what allows a large connector
offering without a driver per service.
Provider    The environment: Local, Generic server, Azure, AWS, Google Cloud,
            Oracle Cloud, Snowflake, Databricks, and so on. A provider holds no
            logic; it only groups services and supplies sensible defaults.
Connector   The service you actually connect to: "Azure SQL Database",
            "Amazon RDS PostgreSQL", "Google BigQuery", "DuckDB". A connector
            declares its fields, its default port, and one engine.
Engine      The technical engine: postgresql, mysql, sqlserver, oracle,
            sap_hana, ingres, sybase_ase, odbc_generic, duckdb, mongodb, and
            others. The engine decides the SQL dialect and the catalog queries.
Adapter     The code that executes the work for one engine: connect, test,
            preview, count, list schemas / tables / views / columns. Written
            once per engine, shared by every connector that declares it.
A cloud service is not a new engine when it reuses an existing one. Example:
  {
    "family": "Cloud",
    "provider": "AWS",
    "connector_service": "aws_rds_postgresql",
    "connector_label": "Amazon RDS PostgreSQL",
    "engine_type": "postgresql"
  }
The engine stays postgresql, so the PostgreSQL adapter and the PostgreSQL
dialect apply unchanged.
2) File reference
data_sources.json (workspace)
  One top-level object per profile name. Each profile keeps the five identity
  fields (family, provider, connector_service, connector_label, engine_type)
  and the connector's non-sensitive parameters. Optional keys not shown on the
  form can be added by editing data_sources.json:
    sql_before_select   Statements run before the assistant's generated SELECT
                        (DuckDB when Local; the profile's connector when one is
                        selected).
    sql_before_create   Prepended to the creation scripts generated for this
                        profile (remote WYSIQ_QUERY Query catalogue, DDL
                        scripts shown for a DBA).
db_connection.json (workspace, optional — edit it with a text editor,
then ⟳ Reload in Data Sources)
  Overrides the connector catalog: connector keys, labels, icons and the list
  of form fields. Keys starting with an underscore are documentation only. A
  field may carry "hidden": true to hide it without removing legacy keys from
  old profiles. volatile_field_keys lists the field names treated as secrets.
connection_type/<connector>/ (workspace)
  One folder per connector, created with the workspace. It contains the
  connector definition and, for SQL connectors, editable SQL templates such as
  list_tables.sql. Your workspace copy overrides the version shipped with the
  application, so a DBA can review and adjust a query. Placeholders such as
  __MAX_OBJECT_NAMES__ are substituted at run time.
connexions/bundled/dialect_lexicon.json (+ optional workspace overlay)
  The dialect data: identifier quoting per style (MySQL backticks, ANSI double
  quotes, SQL Server brackets), the mapping engine to style, bind parameter
  style, case-insensitive LIKE, catalog queries, and the routing table that
  binds each engine to its adapter entry points. A workspace
  dialect_lexicon.json is merged on top (recursive merge; overlay keys starting
  with an underscore are ignored).
connexions_cache/ (workspace)
  Cached object lists produced when you build a catalog for the SQL Assistant.
  Discovery only; nothing is executed on the server.
3) How a connection is resolved
When you press Test, Connect or Catalog, WysiQ:
  1. reads the profile and takes connector_service (or __type__);
  2. resolves it to an engine through connection_type/<key>/, which yields
     engine_type;
  3. asks the registry for that engine's adapter;
  4. lets the adapter open the connection, using the dialect for quoting,
     LIMIT syntax and catalog SQL.
An engine with no adapter is refused with a clear message rather than a silent
failure. This single path is used by Test, the SQL Assistant, the Table Catalog
and the Save flows, so behaviour is identical everywhere.
4) Secrets
Session secrets are held in memory and cleared when the profile or the
application closes.
These are never written to any file: access_token, refresh_token,
client_secret, private_key, secret_access_key, service_account_private_key.
A credential-store reference or an external secret identifier may be stored —
the reference, never the value.
Passwords depend on the PWD toggle in Data Sources. Off (the default) means
session only. On means the profile receives password_enc, obfuscated so the
file cannot be read at a glance. That obfuscation is not strong encryption:
someone holding the file and the application can recover the password. Keep it
off for production credentials.
Tokens and passwords are masked in traces and error messages.
5) Dialects and identifiers
The dialect lexicon holds, per engine, only data: the quote characters, the
LIMIT or TOP form, the bind style, the case-insensitive LIKE operator, and the
catalog queries for schemas, tables, views and columns. All the logic that
composes SQL from that data lives in the shared adapter, once.
That is why adding a dialect is a data change, and why every engine formats
identifiers consistently in the SQL Assistant, in the script shown by the SQL button of the Export Table window, and when
converting a SELECT for local DuckDB materialization.
6) Optional dependencies
No database driver is imported at startup; a missing package cannot stop WysiQ
from launching. The driver loads on first connection. If it is absent, the
message names the exact pip package for the interpreter running WysiQ. Typical
packages: psycopg2-binary (PostgreSQL), mysql-connector-python (MySQL,
MariaDB), pyodbc (SQL Server, Ingres, Db2, Sybase ASE, generic ODBC), oracledb
(Oracle), hdbcli (SAP HANA), pymongo (MongoDB).
Connectors whose engine is not wired into this build remain visible so profiles
can be prepared; Test states that plainly instead of reporting a false success.
7) Compatibility
Profile files are stable. The five identity fields are always written and read
back as they are, so existing profiles keep working across upgrades. Adding a
connector does not change the format; it adds a description.
8) Quest / Toad Intelligence Central
Data Sources: Server family, Quest Software provider, Quest — Toad Intelligence
Central connector. Enter the TIC host, SQL port 3566 (not 8066), the database
containing the published objects, and a TIC-local username/password. The
connector uses MySQL with UTF-8 character set. The catalogue includes
published tables, views, snapshots and datasets. TIC Data Connectivity licence
and the required access rights are needed. WysiQ's generic MySQL driver does
not provide TIC Windows-integrated authentication; use a local TIC account.
When a remote non-MySQL view rejects MySQL SQL, Quest recommends publishing a
snapshot. This is not a direct API connection to the Toad desktop application.
