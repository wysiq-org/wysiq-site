Connexions aux bases — fichiers, modèles SQL et dialectes (WysiQ)

Cette note explique comment les champs affichés dans Sources de données
correspondent aux fichiers sur disque, comment un connecteur est résolu vers un
moteur, où vivent les modèles SQL, et comment les identifiants sont cités selon
le dialecte.
Voir aussi : help/fr/datasource.txt (la fenêtre Sources de données)
             help/fr/params_db_connection.txt (fichiers JSON des profils)
             help/fr/save_dialog_create.txt (CREATE local et exports)
1) Les quatre niveaux
WysiQ sépare quatre notions. C'est cette séparation qui permet une offre large
de connecteurs sans un pilote par service.
Fournisseur  L'environnement : Local, serveur générique, Azure, AWS, Google
             Cloud, Oracle Cloud, Snowflake, Databricks, etc. Un fournisseur ne
             contient aucune logique ; il regroupe des services et fournit des
             valeurs par défaut.
Connecteur   Le service auquel vous vous connectez réellement : « Azure SQL
             Database », « Amazon RDS PostgreSQL », « Google BigQuery »,
             « DuckDB ». Un connecteur déclare ses champs, son port par défaut
             et un moteur.
Moteur       Le moteur technique : postgresql, mysql, sqlserver, oracle,
             sap_hana, ingres, sybase_ase, odbc_generic, duckdb, mongodb, etc.
             Le moteur détermine le dialecte SQL et les requêtes de catalogue.
Adaptateur   Le code qui exécute le travail pour un moteur : connexion, test,
             aperçu, comptage, listage des schémas / tables / vues / colonnes.
             Écrit une seule fois par moteur, partagé par tous les connecteurs
             qui déclarent ce moteur.
Un service cloud n'est pas un nouveau moteur lorsqu'il en réutilise un
existant. Exemple :
  {
    "family": "Cloud",
    "provider": "AWS",
    "connector_service": "aws_rds_postgresql",
    "connector_label": "Amazon RDS PostgreSQL",
    "engine_type": "postgresql"
  }
Le moteur reste postgresql : l'adaptateur PostgreSQL et le dialecte PostgreSQL
s'appliquent sans changement.
2) Référence des fichiers
data_sources.json (workspace)
  Un objet par nom de profil. Chaque profil conserve les cinq champs d'identité
  (family, provider, connector_service, connector_label, engine_type) et les
  paramètres non sensibles du connecteur. Des clés optionnelles absentes du
  formulaire peuvent être ajoutées en éditant data_sources.json :
    sql_before_select   Instructions exécutées avant le SELECT généré par
                        l'assistant (DuckDB en local ; le connecteur du profil
                        lorsqu'un profil est sélectionné).
    sql_before_create   Ajouté en tête des scripts de création générés pour
                        ce profil (catalogue distant de Queries WYSIQ_QUERY,
                        scripts DDL affichés pour un DBA).
db_connection.json (workspace, optionnel — à éditer avec un éditeur de texte,
puis ⟳ Reload dans Sources de données)
  Surcharge le catalogue de connecteurs : clés, libellés, icônes et liste des
  champs du formulaire. Les clés commençant par un tiret bas sont de la
  documentation. Un champ peut porter "hidden": true pour être masqué sans
  retirer d'anciennes clés des profils existants. volatile_field_keys liste les
  noms de champs traités comme des secrets.
connection_type/<connecteur>/ (workspace)
  Un dossier par connecteur, créé avec le workspace. Il contient la définition
  du connecteur et, pour les connecteurs SQL, des modèles SQL modifiables comme
  list_tables.sql. Votre copie prime sur celle fournie avec l'application : un
  DBA peut donc revoir et ajuster une requête. Les marqueurs tels que
  __MAX_OBJECT_NAMES__ sont substitués à l'exécution.
connexions/bundled/dialect_lexicon.json (+ surcharge workspace optionnelle)
  Les données de dialecte : citation des identifiants par style (accents graves
  MySQL, guillemets ANSI, crochets SQL Server), correspondance moteur vers
  style, style des paramètres liés, LIKE insensible à la casse, requêtes de
  catalogue, et la table de routage qui relie chaque moteur aux points d'entrée
  de son adaptateur. Un dialect_lexicon.json du workspace est fusionné par
  dessus (fusion récursive ; les clés de surcharge commençant par un tiret bas
  sont ignorées).
connexions_cache/ (workspace)
  Caches des listes d'objets produits lors de la génération d'un catalogue pour
  l'Assistant SQL. Découverte seule ; rien n'est exécuté sur le serveur.
3) Comment une connexion est résolue
Quand vous cliquez sur Test, Connect ou Catalog, WysiQ :
  1. lit le profil et prend connector_service (ou __type__) ;
  2. le résout vers un moteur via connection_type/<clé>/, qui fournit
     engine_type ;
  3. demande au registre l'adaptateur de ce moteur ;
  4. laisse l'adaptateur ouvrir la connexion, en utilisant le dialecte pour la
     citation, la syntaxe LIMIT et le SQL de catalogue.
Un moteur sans adaptateur est refusé avec un message clair, plutôt qu'un échec
silencieux. Ce chemin unique est utilisé par le Test, l'Assistant SQL, le
Catalogue de tables et les flux Save : le comportement est donc identique
partout.
4) Secrets
Les secrets de session sont conservés en mémoire et effacés à la fermeture du
profil ou de l'application.
Ne sont jamais écrits dans un fichier : access_token, refresh_token,
client_secret, private_key, secret_access_key, service_account_private_key. Une
référence vers un gestionnaire de secrets ou un identifiant externe peut être
enregistrée — la référence, jamais la valeur.
Les mots de passe dépendent de la case PWD de Sources de données. Décochée (par
défaut), le mot de passe reste en session. Cochée, le profil reçoit
password_enc, brouillé de sorte que le fichier ne soit pas lisible d'un coup
d'œil. Ce brouillage n'est pas un chiffrement fort : quiconque possède le
fichier et l'application peut retrouver le mot de passe. Laissez la case
décochée pour des identifiants de production.
Les jetons et mots de passe sont masqués dans les traces et les messages
d'erreur.
5) Dialectes et identifiants
Le lexique de dialecte ne contient, par moteur, que des données : les
caractères de citation, la forme LIMIT ou TOP, le style des paramètres liés,
l'opérateur LIKE insensible à la casse, et les requêtes de catalogue pour les
schémas, tables, vues et colonnes. Toute la logique qui compose le SQL à partir
de ces données vit dans l'adaptateur partagé, une seule fois.
C'est pourquoi ajouter un dialecte est un changement de données, et pourquoi
chaque moteur formate les identifiants de façon cohérente dans l'Assistant SQL,
dans le script affiché par le bouton SQL de la fenêtre Export Table, et lors
de la conversion d'un SELECT pour une
matérialisation locale DuckDB.
6) Dépendances optionnelles
Aucun pilote de base n'est importé au démarrage : un paquet manquant ne peut pas
empêcher WysiQ de se lancer. Le pilote est chargé à la première connexion. S'il
est absent, le message nomme le paquet pip exact pour l'interpréteur qui exécute
WysiQ. Paquets usuels : psycopg2-binary (PostgreSQL), mysql-connector-python
(MySQL, MariaDB), pyodbc (SQL Server, Ingres, Db2, Sybase ASE, ODBC générique),
oracledb (Oracle), hdbcli (SAP HANA), pymongo (MongoDB).
Les connecteurs dont le moteur n'est pas câblé dans cette version restent
visibles pour permettre de préparer un profil ; le Test l'indique clairement
plutôt que de signaler un faux succès.
7) Compatibilité
Le format des profils est stable. Les cinq champs d'identité sont toujours
écrits et relus tels quels : les profils existants continuent de fonctionner
après une mise à jour. Ajouter un connecteur ne change pas le format ; cela
ajoute une description.
8) Quest / Toad Intelligence Central
Dans Sources de données : Famille Server, Fournisseur Quest Software,
Connexion Quest — Toad Intelligence Central. Entrer le serveur TIC, le port
SQL 3566 (pas 8066), la base contenant les objets publies, et le compte TIC.
Le connecteur utilise MySQL avec charset UTF-8. Les tables, vues, snapshots
et datasets publies sont proposes par le catalogue. Il faut une licence TIC
Data Connectivity et les droits appropries. L'authentification Windows
integree n'est pas prise en charge par ce pilote WysiQ : utiliser un compte
TIC local. Une vue executee sur une base non-MySQL peut refuser du SQL MySQL ;
Quest recommande alors de publier un snapshot. Aucune API Toad Desktop
n'est necessaire et aucun acces direct a la session Toad n'est fourni.
